# 3D 編集アプリにおける単体テスト対象の選び方

## 目的

3D 編集系（線路配置 / オブジェクト配置）アプリで「どこを単体テストすべきか」をはっきりさせ、バグを早期に検出しつつ、テストコストを抑える指針をまとめる。ここでは **幾何計算** と **判定ロジック** を中心に整理する。

## 前提（本プロジェクト想定）

- Vue + TresJS(three.js) でシーンをレンダリング。
- 状態は Pinia ストアで管理（rails / scenery / train など）。
- レールは直線・カーブ・勾配・複合（カーブ＋勾配）など種類あり。
- ループ完成判定（周回チェック）やスナップ位置補正など計算処理が存在。
- まだテストフレームワーク（Vitest/Jest等）は未導入。

## なぜ全部はテストしないのか

3D / UI レイヤは視覚的要素依存が強く、スナップショットや E2E での確認が向いている。一方、**座標生成・接続判定・ループ判定** のような「純粋計算」は入力→出力が明確で壊れやすい。ここを優先的にテストすることで改修の安全度が一気に上がる。

## テスト分類マップ

| 分類 | 例 | 推奨テスト種別 | 優先度 |
|------|----|----------------|--------|
| 幾何生成 (Pure) | レール頂点列 / 姿勢(heading,pitch) / カーブ分割 | 単体 | ★★★★☆ |
| 接続判定 | 端点距離 / 角度許容 / 高さ連続性 | 単体 | ★★★★☆ |
| ループ完成検出 | グラフ構築 + 巡回チェック | 単体 + 端境界ケース | ★★★★☆ |
| スナップ計算 | マウス位置→地形平面→最寄端点 | 単体 | ★★★☆☆ |
| プリセット生成 | オーバル / S 字 / 勾配入り | 単体（ゴールデン比較） | ★★★☆☆ |
| シリアライズ | JSON 変換 / バージョン番号付与 | 単体 | ★★☆☆☆ |
| Undo/Redo（予定） | コマンド適用・巻き戻し | 単体（状態差分） | ★★☆☆☆ |
| Three.js 表示 | マテリアル / ライティング | 目視 or スクショ | ★☆☆☆☆ |
| カメラ操作 | 回転制御 / 制限角度 | 簡易統合 (E2E) | ★☆☆☆☆ |

## 「幾何計算」テスト方針

### 1. レール直線ジオメトリ

入力: 長さ L、方向ベクトル (heading)、高さ差 0  
検証:

- 生成頂点数 = 設計値
- 始点(0,0,0)、終点(L,0,0) を heading 回転後に一致（許容誤差内）

### 2. カーブ（円弧）

入力: 半径 R、角度 θ、分割数 n  
検証:

- 各頂点が同一中心から半径 R±ε
- 弧長 ≒ R*θ （頂点列から近似長を求め比較）
- 法線方向一貫性（隣接点ベクトルの回転方向）

### 3. 勾配 + カーブ複合

入力: 半径 R、角度 θ、総上昇量 H  
検証:

- XY 投影は純カーブと同一条件成立
- Z はパラメトリックに 0→H で単調増加
- 姿勢 pitch が接線方向で連続（隣接差分が極端ジャンプしない）

### 4. heading / pitch / quaternion 計算

入力: 開始点 A、終了点 B  
検証:

- heading = atan2(Δx, Δz)（プロジェクト仕様の軸系に合わせる）
- pitch = atan2(Δy, 水平距離)
- 四元数→オイラー→再構築で元と同等（角度差 ε 以下）

### 5. 分割数自動決定ロジック

入力: 半径 R、角度 θ  
検証: 目標セグメント長 targetLen を与えた場合 |実際長 - targetLen| <= 許容割合

## 「判定ロジック」テスト方針

### 1. 接続許容判定

Case:

- 距離 0（完全一致） → OK
- 距離 < tolerance → OK
- 距離 = tolerance + ε → NG
- 角度差 toleranceAngle 以内/超過

### 2. ループ完成検出

最小ケース:

- 3 本三角形 (閉路) → true
- 直線列 (鎖状) → false
- 分岐あり (閉路 + 伸びた枝) → true
- 自己交差（数値誤差でほぼ接続）→ tolerance 以下ならマージして閉路扱い
検証観点:
- 重複ノード生成しない（端点クラスタリング）
- 計算量: N レールで O(N + E) 程度（無限ループしない）

### 3. スナップ計算

入力: マウス射線(Ray)、地面平面、既存端点群

- 最寄端点が距離 d < snapThreshold → その端点座標を返す
- しきい値超過 → 補間丸め（グリッド）
- 斜面/高さが存在する場合 → 高さ補正が正しいか

### 4. 衝突/重なり（将来）

- 新レール bbox vs 既存 bbox
- 交差許容パターン（踏切など）は例外扱い

## テストしない/後回し領域の明示

- Vue テンプレートの表示条件（スナップショット冗長化防止）
- Three.js マテリアルの細部（見た目は人間判断）
- デバイス入力（マウスドラッグの秒単位挙動）

## 浮動小数誤差対策

ヘルパーを 1 つ用意:

```ts
export function expectClose(a: number, b: number, eps = 1e-6) {
  expect(Math.abs(a - b)).toBeLessThanOrEqual(eps);
}
```

配列比較は要素毎に上記を適用。三次元ベクトルは util で短縮。

## ゴールデンファイル戦略（プリセット等）

- presets/(name).json を生成後、 `JSON.stringify` した文字列を比較。
- テストが壊れたら: 仕様変更なのか単なるバグかを PR レビューで判断。

## 関数の pure 化リファクタ指針

| 対象 | 現状想定 | pure 化方法 |
|------|----------|--------------|
| レール頂点列生成 | メソッド内で state 参照 | 引数に長さ/角度/半径を全注入 |
| ループ判定 | store の rails 配列直参照 | rails: Rail[] を渡す関数へ切出し |
| スナップ | Vue component 内 watch で計算 | `(ray, endpoints, params) => result` 関数化 |

## 実装ステップ案

1. テストフレームワーク導入 (例: `devDependencies` に vitest + @types/node)。
2. `src/geometry/` フォルダを作り幾何計算関数を移動。
3. heading/pitch/curve 生成関数を pure 化。
4. ループ判定関数を `src/logic/loop.ts` へ抽出。
5. 最優先 5 ケース（直線/カーブ/勾配/接続判定/ループ判定）テスト作成。
6. スナップ計算 & プリセット生成テスト追加。
7. ゴールデンファイル（プリセット）導入。
8. CI で `vitest run` を実行（GitHub Actions など）。

## 失敗しやすい落とし穴

| 落とし穴 | 回避策 |
|----------|--------|
| カーブ分割数変更でプリセット期待値崩壊 | ゴールデン更新は PR で明示レビュー |
| 浮動小数差で度々失敗 | eps を用途別に (位置=1e-6, 長さ=1e-5, 角度=1e-4) |
| ループ判定で微小ギャップ未吸収 | 端点クラスタリング時に距離 threshold を 1 箇所に定義 |
| テストから Three.js 直接 import して重い | 幾何関数を three 依存なしで書く (Vector3 の最小自前型でも可) |

## メトリクス（ゴールを数値化）

- lines of test target: geometry + logic 用ソース合計行数に対し 80% 以上ステートメントカバレッジ
- 重要ロジック（ループ判定/スナップ）: 分岐カバレッジ 90% 目標

## 将来拡張

- Undo/Redo コマンド履歴の property-based test (fast-check) 導入
- ループ判定を複数閉路対応に拡張する前にテストを先行追加
- 並列（Web Worker）移行時に pure 関数であることを活かし差分比較

## まとめ

1. 最優先は「幾何生成」「接続/ループ判定」など pure / deterministic 領域。
2. 浮動小数誤差は許容幅を共通化し flaky を避ける。
3. プリセット等はゴールデンファイルで構造ごと検証。
4. Three.js 依存を薄めるために関数抽出 → テスト容易化。
5. 先にテストフォルダ構成と pure 化を行うと、後続機能追加の安全性が向上する。

以上。次は Vitest 導入と geometry 関数抽出から着手するのが最も効果が高い。
